# 港美股财务提取适配方案

调研日期：2026-10-21。本文基于当前代码和项目实际配置的进门 Comein MCP；未修改模型运行代码。

建议采用“市场取数适配器 + 披露口径配置 + 统一财务模型”。市场适配器解决接口差异，披露口径配置决定费用如何组成，统一模型负责预测与估值。不能只增加中文别名，也不需要为三个市场复制整套建模流程。

**实际验证范围**

调用了 `company_finance_search`、`pricePerformance`、`get_stock_details`、`get_financial_snapshot`，并保存了实际工具定义。以 FY2023—FY2025 作固定比较窗口；这是历史口径测试，并非最新可用财年的发现测试。

**最直接的报错原因**

1. 港股来源标签不符合当前白名单。泡泡玛特、腾讯即使指定 `statementType=["IS"]` 或 `["BS"]`，返回数值的 `source` 仍为“财务指标”。`fetch.py:312` 会丢弃该来源下除“毛利”“息税前利润”外的全部行。放宽来源后，还需处理查询词与真实科目的差异。
2. 现有金额解析不接受币种后缀。`parse_amount("4161.61亿美元")` 返回 `None`，美股大量有效金额被丢弃；每股金额的“美元”后缀也存在同样问题。金额倍率、币种和每股单位应分别解析。
3. 查询词和返回名并不稳定对应。港股需要显式查询“营业总收入”“销售成本”“毛利润”“现金及现金等价物”；美股默认字段中出现“商品及服务收入”“销售一般管理费用”“资产合计”。同一个底层数据在不同请求中还会以不同名称输出。
4. 当前强制要求 16 个利润表字段。港股样本未取得独立研发费用、税前利润、所得税、财务费用等，美股样本没有可靠的基础 EPS、分开的销售及管理费用。即使解决前两点，仍会在核心字段检查处中断。

年度识别需要完善，但不是本次美股报错的直接原因：现有 `_is_annual()` 已接受 `reportPeriod` 以 `Q4` 结尾，实际接受苹果 9 月、微软 6 月的年度记录。不能把问题简单归因于“代码只认 12 月 31 日”。后续仍应显式保存财年标签、实际起止日、累计/单季口径，避免把财年当自然年。

具体补取边界：

- 港股：取得销售费用、管理费用、营业利润、归母净利润、基本 EPS，以及资产负债表主干；本轮测试的查询词中，研发、所得税、税前利润、融资收支未得到完整独立数据。缺少这些项目不能推定为零。
- 美股：取得利润表和资产负债表主干、研发费用等；“销售一般管理费用”“净利润”“所得税”部分返回值存在与原始报表不一致的情况；EPS 模糊匹配会返回“终止经营基本每股收益”“综合每股收益”，不能当作普通基础 EPS。
- 行情：能取得 `stockFullCode`、市场、交易币种、报价时间、股价、`totalShare`；本轮元数据没有证明 `totalShare` 的 ADS/普通股口径，也没有提供完整的报表币种及换汇说明。
- `get_stock_details` 的 `standardized_info` 实际以蛇形字段返回代码及名称，本轮没有返回其描述中提到的完整市场/币种信息；可用行情接口补全。
- `get_financial_snapshot` 能补充最新报告期概览，不能代替三年年度报表；不得拿最新中报覆盖历史年报的缺项。

`searchData=[]` 在本轮被服务端接受，能帮助发现默认科目，但返回的默认集合并不包含所有定向可查字段。例如港股定向查询能取到销售、管理费用，默认集合却没有。因此空列表只适合辅助探测，正式取数应使用经验证的查询清单，并检查关键字段是否覆盖；工具定义没有承诺空列表的完整性。

**必须处理的科目语义问题**

苹果 FY2025 的进门返回“销售一般管理费用 = 621.51 亿美元”。[苹果 2025 Form 10-K](https://www.sec.gov/Archives/edgar/data/320193/000032019325000079/aapl-20250927.htm) 中，实际 SG&A 为 276.01 亿美元、研发为 345.50 亿美元，两者合计才是 621.51 亿美元。也就是说，这个返回值在本样本中对应经营费用合计。如果再单独扣除研发，会重复扣除 345.50 亿美元。

微软也出现同类现象：接口“销售一般管理费用 = 653.65 亿美元”，而[微软 2025 年报](https://www.microsoft.com/investor/reports/ar25/index.html) 的销售营销、一般行政、研发分别为 256.54、72.23、324.88 亿美元，合计正好 653.65。上述现象支持“本轮字段标签映射存在语义偏差”的判断，不足以证明所有公司、所有年度都使用同一映射，不能写死一条全市场减研发规则。

同一微软样本中，接口“净利润 = 1024.99 亿美元”，而“归母净利润 = 1018.32 亿美元”与年报净利润相符；苹果的接口所得税为 212.05 亿美元，而原报表为 207.19 亿美元。差异原因尚未由供应商确认，不能自行认定是少数股东损益、调整项或数据错误后强行抹平。必须保存两者及来源，按目标会计口径处理冲突。

阿里巴巴也提示收入不能只靠别名：本轮美股默认“商品及服务收入 = 1321.5337 亿美元”，而定向“营业总收入 = 1380.6843 亿美元”；后者与返回的营业成本加毛利润基本一致。二者不能无条件视为同义字段。

腾讯还说明披露配置不能只按市场决定：[其 2025 年度业绩公告](https://static.www.tencent.com/uploads/2026/03/18/f78591955e05a6db4e31e128bdaefefa.pdf) 将研发投入作为一般及行政费用变动的原因。接口未单列研发，不意味着没有研发支出，更不能把管理费用与附注中的研发再次相加。

**建议的数据流程**

`标准化标的 → 按市场取数 → 按披露口径整理 → 校验与补缺 → facts.json → 预测及工作簿`

保留 A 股当前路径作为默认配置，增加 HK / US 数据适配器；另设独立的披露口径配置。上市市场、会计准则、费用布局是不同维度，港股不应自动等同 IFRS，美股也不应自动等同所有数据均为原生美元。

第一步先通过标准化代码确认上市证券及发行人。后续请求使用规范代码，返回后再次核对 `stockCode`，避免中文简称歧义。数据索引至少区分标的、财年、实际报告期、累计/单季、会计口径、币种及版本；不能只按年份合并。

每个适配器配置：明确查询词、允许的返回名、允许的来源标签、指标类型、单位、可用的等式推导、冲突处理方式。港股允许经验证的“财务指标”来源承载报表金额，但只接收配置认可的金额科目；同比、利润率、每股指标不能混进同一个金额字段。

建议映射示例：

| 统一概念 | 候选返回字段 | 额外约束 |
|---|---|---|
| 收入 | 营业收入、营业总收入 | 总额边界一致；商品及服务收入需单独验证 |
| 营业成本 | 营业成本、销售成本 | 不得映射营业总成本，后者可能已含期间费用 |
| 毛利 | 毛利、毛利润、营业毛利 | 与收入减营业成本核对 |
| 现金及现金等价物 | 现金及现金等价物 | 与货币资金、受限现金、短期投资分别保留 |
| 资产总额 | 资产总计、资产合计 | 与负债及权益核对 |
| 营运资本 | 净流动资产、营运资本，或流动资产减流动负债 | 延续现模型的定义；不与经营性营运资本混用 |
| 归母净利润 | 归母净利润、经确认的归属于普通股股东利润 | 继续/终止经营、优先股及调整口径需一致 |
| EPS | 基本 EPS、稀释 EPS 分开保存 | 排除综合收益 EPS、终止经营 EPS；确认每股/每 ADS |

“现金及现金等价物”不等同于 A 股“货币资金”的全部覆盖范围；建议明确修改统一概念及展示名称，保留受限现金和短期投资信息，不能只是加一个无条件别名。

**统一数据契约和费用布局**

`facts.json` 保持现有收入、利润、资产负债等系列可供下游读取，同时增加版本号、财年元数据、财务币种、交易币种、来源与质量信息。费用行由披露配置决定，下游必须同步支持可选费用行。

最少保存这些维度：

| 维度 | 需要保存的信息 |
|---|---|
| 标的 | 发行人、上市证券代码、市场、普通股/ADS、ADS 比例及生效时间 |
| 报告期 | fiscal_year、period_start、period_end、annual/YTD/quarter、发布日期、重述版本 |
| 会计口径 | 报告会计准则、reported/adjusted、合并/归母/普通股股东 |
| 数值 | value、currency、scale、amount/per_share/shares/ratio、正负号约定 |
| 证据 | 工具、原始返回字段与值、原始文件、公告链接及表格位置 |
| 状态 | reported、derived、embedded、not_disclosed、not_applicable、unavailable、conflict |

推荐继续用 1e8 作为金额展示倍率，方便兼容现有模型，但把倍率和币种分开。“亿人民币”“亿美元”是展示层的组合结果。原始金额、每股金额、股数和百分比分开解析；没有单位的数值必须有字段及来源依据，不能一律按亿元处理。

费用至少支持三种布局：

1. 销售、管理、研发分别披露。
2. SG&A 合并披露，研发另列；必须先确认 SG&A 不含研发。
3. 综合经营费用披露，或研发已包含于管理费用；以组合项预测，明细只作附注，不重复扣除。

苹果在确认原始报表后适合第二种；腾讯应按实际费用包含关系配置。本轮接口中的美股“销售一般管理费用”在校验之前应标记为冲突，不能直接选第二种。

统一利润桥建议为：

```text
收入 − 营业成本 = 毛利
毛利 − 不重叠的经营费用 + 其他经营净收益 = 营业利润
营业利润 + 非经营净收益 = 税前利润
税前利润 − 所得税 = 净利润
净利润 − 少数股东损益 − 适用的优先股等调整 = 普通股股东利润
```

“其他经营净收益”可以包含有证据支持的差额，但不能吸收来源冲突来制造表面平衡。接口 EBIT、披露营业利润及模型经营利润应分别保留；不能全市场统一把营业利润、EBIT、税前利润相互替代。

缺失信息优先进行同期间、同币种、同会计口径的确定性推导，例如营运资本、毛利，以及已确认合并净利润减归母净利润得到少数股东损益。税前利润和所得税均缺失时，不能拿营业利润减净利润倒推出所得税。

可以由 agent 从年度公告、10-K、20-F 提取补充字段，但必须附来源及表格位置，由规则校验单位和加总关系。agent 不应猜测费用拆分、税率或缺失项为零。

**泡泡玛特可以怎样落地**

进门已覆盖 FY2025 的收入、营业成本、毛利、销售费用、管理费用、营业利润、归母利润、基本 EPS 及资产负债主干。用[公司 FY2025 年度业绩公告，第 2—3 页](https://www.hkexnews.hk/listedco/listconews/sehk/2026/0325/2026032500285.pdf) 补齐融资收支、联营投资收益、税前利润、所得税和少数股东损益后，利润桥可按亿人民币核对：

```text
营业利润                     168.90474
+ 融资收益净额                 0.76495
+ 权益法投资收益               0.69653
= 税前利润                   170.36622
− 所得税                      40.24580
= 净利润                     130.12042
− 少数股东损益                 2.36353
= 归母净利润                 127.75689
```

它的报表币种是人民币，而行情接口返回交易币种 HKD。以人民币 EPS 乘 PE 得到人民币每股价值，必须按明确日期的“港元/人民币”汇率转换后，才可与港币股价比较。不能把 9.61 人民币/股直接当作 9.61 港元/股。

历史基本/稀释加权平均股数、当前发行股数也应分别保存。优先取原报表股数；净利润除 EPS 只能作为分子分母口径相符时的备选推导，EPS 四舍五入会引入误差，EPS 为零也不应导致整个历史财务提取失败。

阿里巴巴应放在普通股适配之后验证：[公司投资者 FAQ](https://www.alibabagroup.com/en-US/faqs-investor-information) 说明每 ADS 对应 8 股普通股。这个比例要在 EPS、股数和目标股价之间一致处理；进门美股返回美元金额、港股返回无币种后缀的金额，还需要确认供应商换汇方式，不能根据“美股”猜报表原币种，也不能无依据反向换回人民币。

**缺项怎样影响流程**

第一步应输出已取得的历史数据及具体缺口，而不是只报“某年缺字段”。可以显示“可用”“待补充”“口径冲突”，并分别判断：历史概览能否展示、费用预测能否运行、EPS 与估值能否运行。

未知的研发费用不填零；如果已证实嵌入管理费用，就使用组合费用布局。若税前/税后桥无法完成，允许保留历史概览，但不进入依赖这些数据的完整利润预测。币种、标的、EPS 基础冲突未解决时，不输出看似完整的目标价。

这样能让取数阶段保留有效成果，同时明确后续究竟还缺什么。仅放宽 `CORE_INCOME` 后直接让现有工作簿运行，仍会因固定费用行、空单元格和错误口径产生问题。

**建议改动位置和实施顺序**

| 位置 | 建议改动 |
|---|---|
| historical_financials/subjects.py | 保留 A 股配置；增加 HK/US 查询、语义映射、来源与披露配置，拆开通用核心和条件科目 |
| historical_financials/fetch.py | 分离取数与归一化；币种/单位解析；按完整报告期索引；逐字段来源和状态；可解释的补缺 |
| historical_financials/write.py | 落事实数据、口径、覆盖与冲突；让后续阶段按能力检查 |
| historical_financials/company_info.py | 证券代码、股价和市值标签随市场及币种变化 |
| operating_cost/schema.py、cost_agent.py | 支持分项费用、SG&A、综合经营费用等布局；历史轨迹和预测采用同一口径 |
| workbook/build.py、certify.py | 动态费用行、币种标题、汇率桥、EPS 基础和利润勾稽；股数不再一律由利润/EPS 重算 |
| peer_valuation/fetch.py、segment_split/schema.py | 一致预期的财年、收入币种、GAAP/调整 EPS、普通股/ADS 基础与主体保持一致 |

已有同业市值展示支持部分币种信息，可复用；主体历史财务、成本预测、共识 EPS 及目标价链条仍需一起核对，不能把“第一步成功”当作全流程完成。

推荐分三步交付：

1. 先完成共用金额/币种/期间解析、港股来源与科目适配、缺口报告。以宁德时代回归，以泡泡玛特端到端补齐利润桥及人民币—港币估值链。
2. 完成费用布局和来源校验，以苹果、微软验证合并费用、实际财年、基础/稀释 EPS；优先从原始报表补缺和解决冲突，再考虑引入第二结构化数据源作比对。
3. 扩展到阿里巴巴等 ADS、多地上市及跨币种标的，验证股数比例、供应商换汇基础、财年与一致预期对齐。银行、保险等另需行业模型，不纳入普通工商企业费用布局的隐含支持范围。

验收使用保存的真实接口响应作为离线样本，配合少量实时抽查。至少验证：A 股原有结果、港股来源标签、美元单位、非 12 月财年、空值与嵌入项、费用不重复扣除、GAAP/调整口径冲突、币种转换、ADS 比例及 EPS 为零/亏损的处理。容差应考虑接口四舍五入，不以微小舍入误差误判冲突。

供应商侧值得确认的内容是：稳定的科目 ID 和原始科目名；科目是否经过标准化或调整；报表原币种与输出币种；换汇日期/汇率；基础及稀释 EPS、股数及 ADS 基础；报告期起止日与重述版本。当前接口返回的展示名和来源标签不足以独立证明这些语义。
